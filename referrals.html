Referral Program
Dec 2025 – May 2026 · Mexico-focused analysis
Prepared by Javier Ruiz · Experience Senior Specialist · Bitso Customer Service  ·  #exp-retail-user-voice-capsule
When a user refers a friend to Bitso, the expectation is simple: friend signs up, reward arrives on Wednesday. What CS saw in April and May 2026 tells a different story. Within weeks of the V3 launch, Referral Program had become the #2 subcategory within Other — and the one with the steepest growth in the group. The contacts weren't noise: they reflected a consistent gap between what the program promised and what users experienced. This capsule follows that chain: what the volume says, what the satisfaction data shows, where the product breaks before CS even gets involved, and what users are asking for in their own words.
01Program Context

Referral Program V3 simplified the experience significantly: refer a friend, they verify their phone number, and the referrer earns $500 MXN — no deposit required. The mechanic was straightforward and the intent was clear. What made the V3 launch period difficult for CS was a timing gap between when the program went live and when the supporting documentation — the public FAQ and the agent CS guide — reflected the new conditions. That window, however brief, is where much of the friction this capsule documents originates.

03Customer Satisfaction (CSI)

High volume is one problem. How users felt about the experience is another — and in this case, both are moving in the wrong direction at the same time. The CSI score for Referral Program contacts has declined every month since launch, which means the program is not only generating more contacts but generating progressively more dissatisfied ones.

Metric definition

CSI — Customer Satisfaction Index
Survey that measures the experience of the user with Bitso on a scale from 1 to 10. Sent once the ticket is set to solved.

Score: Detractor (0–6) = −1  ·  Passive (7–8) = 0  ·  Promoter (9–10) = +1
(Promoters − Detractors) / Total surveys responded

Two months of data, two consecutive drops. April's 40% was already low for a program in its first month. May fell to 30.4%. June's incoming volume — already at 167 tickets by the 11th — signals the load isn't slowing down.

04UX Breakdown — What Breaks Before CS

Not every Referral Program contact was about a misunderstood rule or an unmet expectation. Some of them happened before the user ever had a chance to make sense of the program — because the app itself broke. The failures documented here are product-side. They don't require agent training to fix. They require product decisions.

ℹ️ The UX issues documented here reflect the state of the product during the V3/V3.1 period (Apr – Jun 8, 2026). V4, launched June 9, may address some of these — this is to be confirmed by the Acquisition squad.

Broken flow — code redemption

This failure does not occur on every attempt, but we were able to reproduce it during our own internal test using a real code. Because the code was ours, we could verify in Hubble that the registration didn't go through for either the referrer or the referee — no event was logged on either side. The screenshots below document the flow we went through.

Opens app  →  Gift icon (top right)  →  Rewards hub  →  "Send invitation" screen  →  "I have an invitation code"  →  Types code  →  ❌ "Something went wrong"  →  Contacts CS

Screenshots — Flow documented during internal test

Rewards hub → "Send invitation" → "I have an invitation code" — the entry point for code redemption is buried inside the outbound referral flow.

WhatsApp invitation with code "jvaqs" → code entered in app → "Something went wrong. We're having an issue on our end." — no diagnostic information, only "Try again."

The flow breaks in two places: where the user enters, and what happens when it fails.

🟠 Code entry placed in the wrong flow

To redeem an invitation code, users must navigate through the "Send invitation" screen — a flow designed for referring others, not for being referred. The entry point is mismatched with the user's intent. Someone who received a code is looking to apply it; instead, they end up in an outbound referral flow.

🔴 Generic error screen — zero diagnostic information

The "Something went wrong. We're having an issue on our end." screen offers no diagnostic information. The user cannot tell whether the code is invalid, expired, already used, or if there was a system error. The only action offered is "Try again" — which typically fails again, leading to CS contact.

When the error occurs, the damage goes deeper than a bad UX moment — the failure leaves no trace.

🔴 Silent code registration failure

When a code is entered, no event is logged internally and no record appears in either user's rewards dashboard. The referral link is silently broken — the referrer has no way of knowing the registration didn't go through until their Wednesday payout doesn't arrive.

Confirmed internally: no Hubble event was logged and no record appeared in either user's rewards dashboard for a tested code. The failure is silent on both sides.

And even when the flow works, there's a fourth problem waiting on the other side.

🟠 No referral or reward status visible in-app

Once a referral is made, there is no in-app mechanism to track how many contacts registered, whether their code was applied, or when the Wednesday payout will arrive. Users contact CS reactively — not because something failed, but because the app gives them no information to work with.

These are users who participated, followed the steps, and genuinely expected the program to work as described. The frustration in their words is proportional to the effort they put in. The quotes below are evidence, not illustration.

Additional issues surfaced on June 11

On the same day this capsule was created, three operational pain points were flagged internally — all of them echoing patterns already visible in the V2 data.

Complex and unclear campaign

The A/B structure with two groups, different reward amounts, and different trigger conditions makes the program difficult to explain — both for agents and for users who receive the promotion.

Fragmented information across channels

Different amounts and conditions appeared across email, app, and Help Center at launch. This is the same communication fragmentation pattern that drove V2 contacts.

Display bug — wrong users saw the promotion

A confirmed bug caused some ineligible users to see the referral promotion. After the fix, those users could no longer see it — generating confusion and CS contacts. At least one Brazilian user was shown a Mexican promotion. Users already in V3.1 Control (no rewards by design) were also surfacing as cases.

⚠️ The communication fragmentation at V4 launch mirrors the V2 pattern. The squad resolved the amounts the same day — but the underlying risk of misaligned channels at launch persists and is worth addressing structurally before future versions ship.
07What Users Are Telling Us — And What Could Help

Users didn't ask for the program to be scrapped — they asked for it to work the way it was described. The data points toward specific, bounded interventions. Some have already been addressed. The ones that haven't are worth a direct conversation with the Acquisition squad.

✅ Resolved — FAQ and agent documentation aligned

The public FAQ was updated to reflect the current program mechanics, and agent documentation is now aligned. These were the two most acute sources of contradictory information during the V2 period. Both are confirmed aligned and up to date ahead of V4.

📋 Open — Referral and reward status visible in-app

The survey data is consistent on this: users want to track their referrals without contacting support. A dedicated section showing each referred contact's status, the reward state, and the expected payout day (Wednesday) would address the most frequent reactive contact type in this category. The information already exists internally — surfacing it to users is the gap.

📋 Open — Code entry flow and error feedback

The UX section documents this in detail. The ask here is simple: a diagnostic error message that tells users what went wrong would convert a dead end into an actionable moment — and reduce the contacts that arrive purely because users had nowhere else to turn. Whether this persists in V4 is worth confirming with the squad.

📋 Open — A/B group communication in V4

V4 runs two groups with different reward amounts and trigger conditions. Agents need to know which group a user belongs to in order to give the correct response. This is the same vector that generated confusion in V2 when agents used V1 guidelines. A clear lookup path in Hubble and an explicit macro for each group condition would prevent the same pattern from recurring under a new version.

The squad should confirm that a Hubble lookup path is available for agents to identify a user's group, and that agents have been briefed on the specific handling for each group's conditions.

⚠️ Watch — Eligibility visibility change

After the June 10 Engineering fix, only eligible users see the referral promotion. Users who had already seen the promo before the fix may contact CS asking why it disappeared. This is a known CS risk flagged at launch — agents should be briefed on how to explain the change without amplifying confusion about program eligibility.
